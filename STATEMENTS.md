# TriageOps — Submission Statements

## Problem & Solution

At 2 a.m., a PagerDuty alert fires: POST /orders is returning 500s. The on-call engineer opens the alert, greps through thousands of log lines, reconstructs a timeline by hand, traces the fault through unfamiliar code, guesses at a fix, and then has to prove the fix works — a 20-to-40-minute loop of mechanical, error-prone work. Three bug classes make it worse: crashes with stack traces, silent logic bugs that produce wrong numbers without crashing, and config mistakes visible only after deploy. Multiply that loop by every incident, every team, every week.

TriageOps compresses that loop into a guided workflow measured in minutes. Feed it an incident alert (JSON) and the service's logs. A deterministic Python pipeline — deliberately not an LLM, so it never invents evidence — parses the alert, correlates the matching log lines with surrounding context, resolves every traceback frame to an exact file:line, and runs the project's pytest suite to establish the failing baseline. Then IBM Bob takes over inside the IDE as the reasoning engine: it triages the alert into a timeline with ranked hypotheses, traces the exact faulty code path, proposes a minimal fix as a reviewable diff, applies it, and iterates against the test suite until the incident's tests go green. The pipeline then renders a one-page incident report — timeline, evidence, root cause, fix, verification — the artifact an on-call engineer would otherwise write by hand.

We proved it on a seeded FastAPI service carrying three real bug classes. On incident INC-2026-1042, a KeyError crash on POST /orders, Bob traced the fault to a single dictionary lookup at victim-service/app.py:60, proposed a one-line fix (TAX_RATES.get(region, 0.0)), applied it, and moved the suite from 5 passed / 4 failed to 7 passed / 2 failed — the two remaining failures belonging to two other seeded incidents, deliberately kept separate. The value is straightforward: faster mean time to recovery, fixes verified by tests instead of hope, and a paper trail (every Bob session screenshotted and committed) that turns tribal debugging knowledge into a repeatable process. Stated honestly, the "minutes, not tens of minutes" claim is measured on our seeded incidents, not production outages — but the workflow is exactly the one production teams run, minus the toil.

Then we pointed it at a genuine third-party bug. humanize 4.3.0, the open-source formatting library, crashes with ValueError on metric(0): number.py:511 computes math.log10(abs(0)), and log10(0) is mathematically undefined (upstream issue #57, fixed in 4.4.0 via PR #47). We vendored the exact 4.3.0 release and had Bob work it blind — intake, reproduction, root cause, and a fix proposal derived without seeing the upstream patch. Bob's guard matches the upstream fix's output ("0.00", "0.00 V") on all tested inputs, and its final report compares the two honestly, conceding the upstream one-liner is cleaner. TriageOps doesn't just automate triage — its reasoning stands next to a real maintainer's patch.

## IBM Bob Usage

IBM Bob is the reasoning core of TriageOps — not a code-completion accessory, but the agent that performs the incident-triage loop no deterministic pipeline can: hypothesize, trace, fix, verify, report. All work ran on the hackathon-provisioned account (team ibm-hackathon-lablab), and every task's session consumption summary is screenshotted under bob_sessions/.

Tasks 1–5 (Ask, then Agent mode) closed INC-2026-1042 end to end. Task 1 turned the alert and logs into a minute-by-minute timeline with three ranked, evidence-backed hypotheses. Task 2 traced the KeyError crash to a single dictionary lookup at victim-service/app.py:60 and wrote triage/reports/root_cause_001.md. Task 3 proposed the minimal diff (TAX_RATES.get(region, 0.0)) to triage/fixes/fix_001.diff without applying it. Task 4 applied it and ran pytest: 5 passed / 4 failed → 7 passed / 2 failed, attributing the remaining failures to separate incidents. Task 5 synthesized the one-page incident report, marking uncertainties as uncertain.

Tasks 6–11 repeated the loop for the two remaining seeded incidents, proposed-only. For INC-2026-1043 (tasks 6–8), Bob traced the double-applied bulk discount and wrote root_cause_002.md and fix_002.diff. For INC-2026-1044 (tasks 9–11), Bob traced PAYMENTS_MODE=sandbox raising PaymentError and wrote root_cause_003.md and fix_003.diff. Both fixes were deliberately left unapplied, so the dashboard keeps showing the honest live result: 7 passed / 2 failed.

Tasks 12–16 took on a genuine third-party bug: humanize 4.3.0's metric() crashes on metric(0) with ValueError (upstream issue #57, fixed in 4.4.0 via PR #47), vendored verbatim under triage/realworld/humanize/. Task 12 (Ask) produced the timeline and ranked hypotheses from the alert alone. Task 13 reproduced the crash and wrote root_cause_004.md, tracing it to math.log10(abs(0)) at number.py:511. Task 14 proposed fix_004.diff — a zero-guard — blind, without seeing the upstream patch. Task 15 applied it to the vendored copy and verified: metric(0) → "0.00", neighboring inputs unchanged. Task 16 wrote the incident report, then compared Bob's fix against the actual upstream patch — honestly judging upstream's one-line ternary the cleaner long-term solution.

Total Bobcoin spend stayed well under the 40-coin allocation. The division of labor is deliberate: the deterministic pipeline gathers evidence it cannot hallucinate; Bob does the reasoning, and every claim it makes is anchored to a file, a line, or a test result.
