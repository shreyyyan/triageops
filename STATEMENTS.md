# TriageOps — Submission Statements

## Problem & Solution

At 2 a.m., a PagerDuty alert fires: POST /orders is returning 500s. The on-call engineer opens the alert, greps through thousands of log lines, reconstructs a timeline by hand, traces the fault through unfamiliar code, guesses at a fix, and then has to prove the fix works — a 20-to-40-minute loop of mechanical, error-prone work. Three bug classes make it worse: crashes with stack traces, silent logic bugs that produce wrong numbers without crashing, and config mistakes visible only after deploy. Multiply that loop by every incident, every team, every week.

TriageOps compresses that loop into a guided workflow measured in minutes. Feed it an incident alert (JSON) and the service's logs. A deterministic Python pipeline — deliberately not an LLM, so it never invents evidence — parses the alert, correlates the matching log lines with surrounding context, resolves every traceback frame to an exact file:line, and runs the project's pytest suite to establish the failing baseline. Then IBM Bob takes over inside the IDE as the reasoning engine: it triages the alert into a timeline with ranked hypotheses, traces the exact faulty code path, proposes a minimal fix as a reviewable diff, applies it, and iterates against the test suite until the incident's tests go green. The pipeline then renders a one-page incident report — timeline, evidence, root cause, fix, verification — the artifact an on-call engineer would otherwise write by hand.

We proved it twice. First on a seeded FastAPI service carrying three real bug classes: on incident INC-2026-1042, a KeyError crash on POST /orders, Bob traced the fault to a single dictionary lookup at victim-service/app.py:60, proposed a one-line fix (TAX_RATES.get(region, 0.0)), applied it, and moved the suite from 5 passed / 4 failed to 7 passed / 2 failed — the two remaining failures belonging to two other seeded incidents, deliberately kept separate.

Then on real-world code: incident INC-2026-1045, a genuine bug in humanize 4.3.0 (upstream issue #57) where metric(0) crashes with ValueError because number.py:511 takes the logarithm of zero. Bob reproduced the crash, traced the exact code path, and proposed a fix blind — without ever seeing the upstream patch. Applied to our vendored copy, metric(0) now returns "0.00" with neighboring inputs unchanged. Bob then compared its fix against the real upstream patch (PR #47) and honestly judged the maintainer's one-liner cleaner.

The business value is straightforward: faster mean time to recovery, fixes verified by tests instead of hope, and a paper trail (all sixteen Bob sessions screenshotted and committed) that turns tribal debugging knowledge into a repeatable process. Stated honestly, the "minutes, not tens of minutes" claim is measured on our incidents, not production outages — but the workflow is exactly the one production teams run, minus the toil.

## IBM Bob Usage

IBM Bob is the reasoning core of TriageOps — not a code-completion accessory, but the agent that performs the incident-triage loop no deterministic pipeline can: hypothesize, trace, fix, verify, report. All sixteen tasks ran on the hackathon-provisioned account (team ibm-hackathon-lablab), and every task's session consumption summary is screenshotted under bob_sessions/.

Tasks 1–5 (Ask + Agent modes) closed incident INC-2026-1042 end to end. Task 1: from the alert payload and correlated logs, Bob produced a minute-by-minute timeline, three ranked root-cause hypotheses with file:line evidence each, and a one-sentence most-likely cause — replacing the manual "read the alert, grep the logs" phase. Task 2: working in victim-service/, Bob followed the request path from POST /orders through every function call to the exception, confirming each step against the traceback frames, and wrote triage/reports/root_cause_001.md: the faulty call chain, why region arrived as None, and the blast radius — analysis only, no code changed. Task 3: from that report, Bob proposed the minimal change, wrote the unified diff to triage/fixes/fix_001.diff without applying it, and added a safety rationale covering what could regress and which tests cover the changed lines. Task 4: Bob applied the diff, ran python -m pytest victim-service/tests/ -v, and reported exact before/after counts — 5 passed / 4 failed → 7 passed / 2 failed — with the two remaining failures attributed to separate seeded incidents left untouched; no test expectations were modified. Task 5: Bob synthesized alert, logs, root-cause report, diff, and test results into the one-page factual report at triage/reports/incident_INC-2026-1042_report.md, marking uncertain items as uncertain.

Tasks 6–11 repeated the trace-propose-report loop for the two remaining seeded incidents, proposed-only. For INC-2026-1043 (tasks 6–8), Bob traced the bulk discount applied twice — item level and subtotal level — wrote root_cause_002.md, proposed fix_002.diff removing the second application, and wrote the incident report. For INC-2026-1044 (tasks 9–11), Bob traced PAYMENTS_MODE=sandbox raising PaymentError instead of simulating, wrote root_cause_003.md, proposed fix_003.diff returning "test_sandbox_txn", and wrote the report. Both fixes were deliberately left unapplied, so the dashboard keeps showing the honest live result: 7 passed / 2 failed.

Tasks 12–16 took the same loop to real-world code: humanize issue #57. Task 12 (Ask): intake on the billing-worker alert — timeline and three ranked hypotheses from 30 correlated log lines. Task 13 (Agent): Bob reproduced the metric(0) crash, traced the exact path to number.py:511, and wrote root_cause_004.md. Task 14 (Agent): Bob proposed a two-line zero-guard as fix_004.diff — blind, without seeing the upstream patch. Task 15 (Agent): Bob applied it to the vendored copy and verified — metric(0) → "0.00", neighboring inputs unchanged. Task 16 (Agent): Bob wrote the final report with "Bob vs upstream," comparing its fix against the real PR #47 and honestly concluding the maintainer's ternary is cleaner.

Total Bobcoin spend stayed well under the 40-coin allocation. The division of labor is deliberate: the deterministic pipeline gathers evidence it cannot hallucinate; Bob does the reasoning, and every claim it makes is anchored to a file, a line, or a test result.
